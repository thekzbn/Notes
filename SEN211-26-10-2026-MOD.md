# SEN211: Software Engineering

## 1. Software Problem Specification

Solving a problem using software begins with two things:

1. **Specifying what the system should do.**
2. **Specifying the constraints under which the software must operate.**

These form part of defining the requirements of a software system.

## 2. Engineering Classifications

Software requirements can be classified into two main categories: functional and non-functional requirements.

### 2.1 Functional Requirements

Functional requirements specify what the software must do. They describe the core problems the system was created to solve and the functions it must perform.

For example, a banking application must allow users to perform banking operations such as checking their balances and transferring money.

### 2.2 Non-functional Requirements

Non-functional requirements specify additional qualities, characteristics, and constraints that determine how the software should operate.

They are not necessarily individual functions of the system, but they influence the quality and reliability of the software.

For example, security is a non-functional requirement of a banking application. Although an application might technically perform banking operations without adequate security, that would make it unsuitable for its intended purpose.

Other examples of non-functional requirements include performance, reliability, usability, and maintainability.

## 3. Requirements Validation

A software system can be validated in two related senses: whether it works as intended and whether it meets the user's actual needs.

**Software validation** concerns whether the system meets the needs and expectations of its intended users.

A system may function correctly according to its implementation but still fail to solve the problem it was designed to address.

Therefore, it is not enough to establish that the software works. It must also be established that it meets the specified requirements and fulfils its intended purpose.

## 4. Software Design

Software design is the use of different tools and representations to describe a software system from different perspectives.

It also involves deciding how the system's components are organised, how they interact, and how they respond to different situations.

These representations help developers understand the proposed system before and during its implementation.

## 5. Software Process Models (Software Development Life Cycle)

### 5.1 Introduction to Software Process Models

Not every problem can be solved using software, and not every problem is a software problem.

Once a problem has been identified as suitable for a software-based solution and the proposed solution has been defined, the next step is to determine how to develop that solution.

Software Process Models (SPMs) describe software development as a series of structured activities or stages.

A **process** is a structured set of activities carried out to solve a problem. In software engineering, these activities guide the development of a software solution.

These activities can be represented from different perspectives. Each representation is called a **model**.

Therefore, a software process model represents the activities involved in developing a software system and the relationships between them.

Different models can represent the same software development process from entirely different perspectives.

### 5.2 An Analogy for Understanding Software Process Models

Imagine you want to visit Sandra, who is 48 metres away from you and has just sent you a voice note lasting 3 minutes and 22 seconds.

The different software process models are not the different vehicles you could use to reach her. Instead, imagine that they are the different routes you could take while using the same vehicle to get there.

The destination remains the same, but the route differs.

Similarly, software process models offer different ways of organising and approaching the activities involved in developing software.

## 6. Traditional Software Process Models

Traditional software process models are established approaches to organising software development. They include the Waterfall Model, Prototyping Model, and Spiral Model.

### 6.1 Waterfall Model

The Waterfall Model organises software development into distinct, sequential phases. Each phase is expected to be completed before the next begins.

In its traditional form, the model discourages returning to a previously completed phase. This makes it most suitable for projects in which the requirements are well understood and the proposed solution is clearly defined from the beginning.

**Limitations:**

1. **Inflexibility:** Changes to requirements can be difficult to accommodate once development has progressed.
2. **Limited adaptability:** The rigid sequence makes responding to changing requirements challenging.
3. **Unrealistic planning assumptions:** It can be difficult to predict every requirement and resolve every uncertainty before development begins.

### 6.2 Prototyping Model

The Prototyping Model is useful when the requirements of a software system are unclear or not fully understood.

It involves creating a preliminary, simplified version of the proposed system, known as a **prototype**. The prototype is evaluated and validated to help clarify requirements and establish what the final system should do.

Feedback from users and other stakeholders can then inform the development of the final system.

**Limitations:**

1. **Cost:** Developing and refining prototypes can increase project costs.
2. **Time:** Repeated prototyping and evaluation can extend the development process.

### 6.3 Spiral Model

The Spiral Model combines aspects of the Waterfall and Prototyping approaches. Its defining feature is its emphasis on identifying, evaluating, and reducing risks throughout software development.

Development proceeds through repeated cycles, with each cycle involving activities such as planning, risk analysis, development, and evaluation.

Before proceeding with a stage of development, the risks and associated costs are assessed so that significant problems can be addressed early.

The approach is particularly useful for large or long-term projects with substantial risks. Risk assessments can also help stakeholders decide whether a project should continue or be terminated.

Customer involvement throughout the development process helps ensure that the evolving system continues to meet the customer's needs.

**Advantages:**

1. Risks are identified and addressed throughout development.
2. Customer feedback can be incorporated at different stages.
3. Risk assessments can support informed decisions about whether a project should continue.

**Limitation:**

1. **High cost:** Repeated risk assessment, planning, and evaluation can make the Spiral Model expensive to use.

## 7. Agile Software Development

Agile software development approaches software development through **incremental** and **iterative** processes.

- **Incremental development:** The solution is developed in smaller parts, with each increment adding functionality to the system.
- **Iterative development:** The solution is refined through repeated cycles of development, evaluation, and improvement.

Together, these approaches allow a software system to evolve gradually rather than requiring every detail to be finalised before development begins.

### 7.1 Examples of Agile Approaches and Frameworks

**Extreme Programming (XP):** An Agile software development approach that emphasises practices intended to improve software quality and responsiveness to changing requirements.

**Scrum:** An Agile framework for organising and managing work through defined roles, events, and iterative development cycles. Scrum is more accurately described as a framework for managing product development than as a programming methodology.
